## 3–6. Four GDPR decisions — decision criterion set by @rorar

> *"Most flexible and long-lasting solution for this project BUT completely GDPR
> compliant."*

**This criterion changes at least one earlier recommendation.** Previous advice on
task 3 was pragmatic (keep hard delete, because the anonymise rule as written leaks).
Under *complete compliance* as a hard constraint the answer may invert: GDPR Recital 26
puts genuinely anonymised data **outside the regulation entirely**, so
anonymise-with-full-scrub is simultaneously the most compliant *and* the most flexible
option — it keeps the audit value forever with no retention obligation. Re-derive each
answer against the stated criterion rather than inheriting the earlier one.

Use `/gdpr-data-handling` for each. Record every answer as a decision, not a comment.

### 3. Timeline-activity retention — ownership + policy
Ownership is **already settled** by the specs' own scope headers and needs no judgement:
`gdpr-data-rights.allium` S4 explicitly lists `CrmActivityLog`; `crm-gdpr.allium`
excludes system-wide retention. So `crm-gdpr`'s `ExpireOldTimelineActivities` is
trespassing → delete it, express the hand-off with `deferred`, drop the duplicated
`timeline_retention` config (Allium `patterns.md` Pattern 8: reference, don't copy).

The **policy** half is the real question: `crm-gdpr` anonymises in place,
`gdpr-data-rights.allium:404` hard-deletes, `retention-cron.ts:203` hard-deletes.
Critical fact for whichever way you go — `CrmActivityLog` has **three** PII carriers
(`targetPersonId`, `details`, `linkedRecordName`) and the anonymise rule nulls only the
first, while `crm/AnonymizePerson` scrubs all three. Anonymise-as-specified is therefore
*worse* than deleting. Any anonymise answer must scrub all three.

### 4. Art. 15 export completeness
**13 of 23 Prisma `Person` scalar columns are unexported** — six `address*`, `avatarUrl`,
`createdBySource`/`createdByName`, `updatedBySource`/`updatedByName`, `updatedAt`,
`userId`. Earlier statements of "omits address and avatar_url" were understated twice.

`createdByName`/`updatedByName` are a case nobody has raised: Art. 15(1)(g) entitles a
subject whose data was not collected from them to information about its source.

**Do not settle this by auditing the list** — two successive careful reviews each named
two of thirteen. The durable fix is a test asserting every scalar column on Prisma
`Person` is either exported or in a documented exclusion set. Scope it at **field**
level over models already in `collect-user-data.ts`: the model list *has* been maintained
(Welle 5 added Referral/PersonConnection), but columns added to an existing model
(ROADMAP 1.21's `addressCountryCode`) are invisible to whoever edits the export.
Home: `__tests__/collect-user-data-audit.spec.ts`.

### 5. WH-B3 — retention archives but never erases
`ExpireAutoCreatedPersons` moves `active → archived`; **nothing runs after**.
`crm-cron.ts:71` is the only transition, `retention-cron.ts` never touches `Person`. So
an archived, retention-expired contact keeps name/emails/phones indefinitely. `archived`
is a status flag, not de-identification — Art. 5(1)(e).

Constraint on the fix: the rule requires `status = active`, so if expiry is made to do
something stronger, manually-archived records escape it. Widen that guard in the **same**
change. Full write-up: `docs/BUGS.md` WH-B3.

### 6. Converted-referral dead end
`converted` is terminal (`insideTrack.model.ts:82`, no outgoing edges). A referral whose
Job was deleted shows *"The job application it created has since been deleted"* and has
**no route back** — `commitReferralToApply` and `reviveReferral` are both blocked by the
transition table. The GDPR angle is thin here; this is mostly a product question W-D2
Decision C never asked. Decide whether the state is recoverable or terminal-by-design,
and say so in the UI either way.

build, not the host") is weaker than documented.
